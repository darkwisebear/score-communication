# Rust COM API

## Overview

The **COM API** is a Rust API for service-oriented inter-process communication (IPC) in the `mw::com` ecosystem.
It provides a clean, type-safe way for Rust applications to **offer** and **consume** services using a publish/subscribe event model.

Application code is written against a runtime-agnostic set of concepts (traits and types). At build or deployment time you select a concrete runtime implementation (for example a production runtime, or a mock runtime for tests) without rewriting business logic.

For internal architecture and implementation details, see [high_level_design_detail.md](design/high_level_design_detail.md)

### What This API Is For

- **Build service providers and consumers in Rust** using a common service-oriented model.
- **Keep business logic stable** while the underlying runtime implementation can differ (production vs. test).
- **Make IPC explicit**: offering, publishing, discovering, subscribing, and reading samples are all deliberate operations.

### Conceptual Architecture

At a high level, applications interact with the COM API concepts (Runtime, Producer/Consumer, Publisher/Subscriber). A concrete runtime implementation connects those concepts to the underlying communication technology using an FFI (Foreign Function Interface) layer that bridges the underlying C++ COM API to Rust.

![COM API Architecture Layers](design/architecture_layers.svg)

If you’re interested in the detailed layering, module boundaries, and trait hierarchy, see [high_level_design_detail.md](design/high_level_design_detail.md).

## How It Works

### Service-Oriented Communication Model

The Rust COM API wraps the underlying C++ COM API and exposes a **publish/subscribe** model through type-safe Rust traits and abstractions.
A service is a logical entity with a well-known interface (a set of events and data types) and a location (an `InstanceSpecifier` path like `/vehicle/speed`).

Communication always flows in one direction for a given event: a **Producer** writes data, and one or more **Consumers** receive it.
Rust's traits provide compile-time guarantees and type safety, ensuring both sides only need to agree on the interface definition without knowing about each other at compile time.

### Core Concepts

| Concept | What it means in practice |
|---------|--------------------------|
| **Runtime** | The entry point for creating producers and discovering services. |
| **Producer** | The provider side: offers a service instance and publishes events. |
| **Consumer** | The user side: discovers a service instance and subscribes to its events. |
| **Service discovery** | Finds currently available service instances (availability can change over time). |
| **Publisher / Subscriber** | Typed endpoints for sending (`Publisher<T>`) and receiving (`Subscriber<T>`) event data. |
| **Subscription** | A `Subscription<T>` represents an event stream. |
| **Sample** | `Sample<T>` values are immutable snapshots you read from it. |
| **SampleContainer** | Container for reading samples from the event stream. |
| **InstanceSpecifier** | Path-like service address (e.g. `/vehicle/speed`). |

## Mock Runtime for Testing (mockall)

The production runtime is backed by C++/FFI, which makes it awkward to drive from a Rust unit test. The **`com-api-runtime-mockall`** crate is a `testonly` drop-in implementation of `score_com_concept::Runtime` built on [mockall](https://crates.io/crates/mockall). It lets you run the *same* business logic (including code generated by the `interface!` macro) without any IPC, config file, or backend.

The core idea is **scripted-by-default-inactive**: nothing the mock does has any effect until a test tells it what to do. Every observable decision (build, offer, allocate, send, subscribe, receive, discover) is routed through a `Mock*Policy` object, and a test programs those objects with mockall expectations. If your code calls something you forgot to script, the test panics with a clear "no matching expectation" message rather than silently doing nothing.

### Using the mock runtime

Depend on the `score_com_mockall` re-export target instead of `score_com`. It re-exports the full COM API *plus* the mock types, and keeps the crate name `score_com` so that `interface!`-generated code (which expands to absolute `score_com::…` paths) compiles unchanged:

```python
rust_test(
    name = "my-module-tests",
    crate = ":my_module",
    deps = [
        "//score/mw/com/rust:score_com_mockall",   # instead of :score_com
        "@score_communication_crate_index//:mockall",
        "@score_communication_crate_index//:tokio",
    ],
)
```

`//score/mw/com/rust:score_com_mockall` is marked `testonly = True`, so the mock can only be pulled into test targets — production code can never link it by accident.

### The API

The runtime is `MockRuntimeImpl`; every component you create from it is a thin wrapper around a scriptable `#[automock]` **policy** trait. You configure a policy with mockall expectations, then hand it to the runtime through an `expect_*` method **before** your code runs.

| What your code calls | Policy you script | Scriptable methods | Registered on |
|---|---|---|---|
| `runtime.producer_builder::<I>(spec)` | `MockProducerBuilderPolicy` | `build` | `runtime.expect_producer_builder(&spec, …)` |
| `Producer::offer` / `OfferedProducer::unoffer` | `MockProviderInfoPolicy` | `offer_service`, `stop_offer_service` | `runtime.expect_provider_info(&spec, …)` |
| `Publisher<T>::allocate` / `send` | `MockPublisherPolicy<T>` | `allocate`, `send` | `runtime.registry().expect_publisher(&spec, "event", …)` |
| service discovery | `MockServiceDiscoveryPolicy` | `builders` | `runtime.expect_service_discovery(&spec, …)` |
| `ConsumerBuilder::build` | `MockConsumerBuilderPolicy` | `build` | inside the discovery `builders` result |
| `Subscriber<T>::subscribe` | `MockSubscriberPolicy<T>` | `subscribe` | `runtime.registry().expect_subscriber(&spec, "event", …)` |
| `Subscription<T>::try_receive` / stream | `MockSubscriptionPolicy<T>` | `poll_samples`, `unsubscribe` | `runtime.registry().expect_subscription(&spec, "event", …)` |

Policies for a given instance/event are stored in the shared **`MockRegistry`** (a cloneable `Arc`-backed map keyed by `(instance, event, component)`). The generated constructors pop the pre-registered policy out when they run, so a clone of the same handle shares the same expectations — which is exactly what `interface!` does, since it clones the info handle once per event.

The receive side is driven by `poll_samples`, which returns a `PollOutcome`:
- `PollOutcome::Ready(vec![…])` — deliver these samples;
- `PollOutcome::Retry` — nothing yet, poll again;
- `PollOutcome::Idle` — nothing, and nothing more is coming (a stream parks here).

### A small example test

The test below scripts a minimal producer→consumer round trip against the generated `Vehicle` interface and asserts one scripted tire flows through. It uses only the synchronous API, so it is a plain `#[test]`. (The mirrored, more complete version lives in [`tests_using_mockall_runtime.rs`](../example/com-api-example/tests_using_mockall_runtime.rs).)

```rust
use mockall::predicate::eq;
use score_com::{
    Builder, FindServiceSpecifier, InstanceSpecifier, MockConsumerBuilderPolicy,
    MockProviderInfoPolicy, MockProducerBuilderPolicy, MockPublisherPolicy,
    MockRuntimeImpl, MockServiceDiscoveryPolicy, MockSubscriptionPolicy,
    MockSubscriberPolicy, PollOutcome, Producer, Publisher, Runtime, SampleContainer,
    SampleMaybeUninit, SampleMut, ServiceDiscovery, SharedConsumerBuilder, Subscriber,
    Subscription,
};
use com_api_gen::{Tire, VehicleInterface};

#[test]
fn scripted_round_trip_delivers_one_tire() {
    let runtime = MockRuntimeImpl::new();
    let spec = InstanceSpecifier::new("/Vehicle/Service1/Instance").unwrap();

    // 1) Producer side — script what `offer()` + `send()` will touch.
    let mut pb = MockProducerBuilderPolicy::new();
    pb.expect_build().times(1).returning(|| Ok(()));
    runtime.expect_producer_builder(&spec, pb);

    let mut offer = MockProviderInfoPolicy::new();
    offer.expect_offer_service().times(1).returning(|| Ok(()));
    runtime.expect_provider_info(&spec, offer);

    // `offer()` creates a Publisher for EVERY event. Script the one we use…
    let mut tire_pub = MockPublisherPolicy::<Tire>::new();
    tire_pub.expect_allocate().returning(|| Ok(()));
    tire_pub.expect_send().returning(|_| Ok(()));
    runtime.registry().expect_publisher(&spec, "left_tire", tire_pub);
    // …and register (but leave unscripted) the others, e.g. `exhaust`.
    runtime.registry().expect_publisher(&spec, "exhaust",
        MockPublisherPolicy::<com_api_gen::Exhaust>::new());

    // 2) Consumer side — discovery hands back a builder, which builds the consumer.
    // Build the `SharedConsumerBuilder` up front (it owns the scripted policy
    // and is `Clone`, so the closure can hand out a clone on every call).
    let mut cb = MockConsumerBuilderPolicy::new();
    cb.expect_build().times(1).returning(|| Ok(()));
    let builder = SharedConsumerBuilder::from_policy(
        spec.clone(), runtime.registry().clone(), cb,
    );
    let mut disc = MockServiceDiscoveryPolicy::new();
    disc.expect_builders()
        .returning(move || Ok(vec![builder.clone()]));
    runtime.expect_service_discovery(&spec, disc);

    // `Consumer` builds a Subscriber for every event too.
    let mut tire_sub = MockSubscriberPolicy::<Tire>::new();
    tire_sub.expect_subscribe().with(eq(5)).times(1)
        .returning(move |max| { assert_eq!(max, 5); Ok(()) });
    runtime.registry().expect_subscriber(&spec, "left_tire", tire_sub);
    runtime.registry().expect_subscriber(&spec, "exhaust",
        MockSubscriberPolicy::<com_api_gen::Exhaust>::new());

    // The subscription replays exactly one scripted tire, then idles.
    let mut tire_s = MockSubscriptionPolicy::<Tire>::new();
    tire_s.expect_poll_samples().returning(|_| {
        Ok(PollOutcome::Ready(vec![Tire { pressure: 42.0 }]))
    });
    runtime.registry().expect_subscription(&spec, "left_tire", tire_s);

    // 3) Now run the same business code a real test would.
    let offered = runtime
        .producer_builder::<VehicleInterface>(spec.clone())
        .build().unwrap()
        .offer().unwrap();
    offered.left_tire
        .allocate().unwrap()
        .write(Tire { pressure: 42.0 })
        .send().unwrap();

    let consumer = runtime
        .find_service::<VehicleInterface>(FindServiceSpecifier::Specific(spec.clone()))
        .get_available_instances().unwrap()
        .into_iter().next().unwrap()
        .build().unwrap();
    let sub = consumer.left_tire.subscribe(5).unwrap();

    let mut buffer = SampleContainer::new(5);
    let added = sub.try_receive(&mut buffer, 5).unwrap();
    assert_eq!(added, 1);
    assert_eq!(buffer.iter().next().unwrap().pressure, 42.0);
}
```

Reading it top to bottom: lines marked **1)** and **2)** are the *scripting* phase — you declare, for each component, what to return and how many times. Lines in **3)** are ordinary COM API calls, identical to what you would write against the production runtime. The assertion at the end checks the scripted value actually round-tripped.

### Why it is built this way

Two mockall limitations drive the design:

1. **The GAT wall.** mockall 0.14 cannot `#[automock]` a trait that has generic associated types. Three COM traits do: `Runtime`, `Publisher::SampleMaybeUninit<'a>`, and `Subscription::Sample<'a>`. So those traits get *hand-written* `Mock*` wrappers that only exist to carry the associated types and lifetimes. All the actual scriptable behaviour lives on lifetime-free `*Policy` traits (`PublisherPolicy<T>`, `SubscriberPolicy<T>`, `SubscriptionPolicy<T>`, …), which *are* `#[automock]`-ed. This keeps the part mockall can't handle tiny and mechanical, and the part it *can* handle fully in its idiom.

2. **Macro-constructed endpoints.** `interface!` builds `Publisher`/`Subscriber`/discovery internally from `R::ProviderInfo` / `R::ConsumerInfo`, so a test cannot inject a pre-configured mock for them. Instead, both info handles carry the shared `MockRegistry`, and a test pre-registers policies up front keyed by `(instance, event)` (or per instance for discovery/producer-builder/provider-info). The generated constructors pop the matching policy out when they run. This is why the example above registers a policy for every event, even the ones it never touches — `interface!` constructs all of them.

The net result: a single `MockRuntimeImpl` + `expect_*` calls give you a fully controllable double of the runtime, with mockall's `times(n)`, `.with(predicate)`, and `returning(closure)` for asserting call counts, argument values, and injecting failures (e.g. making `allocate` return an `Error` to test error handling).
